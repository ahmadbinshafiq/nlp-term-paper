1. **AgentRewind: Recoverable Execution for Long-Horizon LLM Agents** — Yu Zhuang, Kefei Chen, Yitong Duan, Shuxin Zheng, Jian Li, Xu-Yao Zhang (2026) arXiv preprint arXiv:2608.14380 (submitted 14 Aug 2026; comments: 19 pages, 5 figures)
   https://arxiv.org/abs/2608.14380 | code: https://github.com/Futuresis/replay-agent-recorder (code); https://github.com/Kelvin-Coffee/MettleBench (benchmark data)
   family: checkpoint
   AgentRewind is a runtime recovery framework for long-horizon LLM agents that records aligned checkpoints of both the agent context and a controlled environment, so an agent can return to an earlier state and resume with information from previous attempts. The authors also build MettleBench, 82 long-horizon engineering tasks (derived from Terminal-Bench 2.0, ProgramBench, SWE-bench, ProjectEval, GitTaskBench) with ordered acceptance checklists (640 criteria total). Across models, execution strategies and three agent harnesses, AgentRewind improves task success and checklist-prefix progress over baselines.
   relevance: Clean academic instance of the checkpoint family: per-step aligned context+environment snapshots enable rewind/resume, which is exactly counterfactual re-execution from step k. Evaluation is limited to task success, checklist progress, recovery effectiveness and ablations (env rewind vs context rewind vs rewind memory) - no failure-localization, evidence-tracing or reconstruction-fidelity metrics - so it serves as a ready-made checkpoint baseline. The public recorder (JSONL traces, record/replay/fork, HTML/Mermaid trace export) is directly instrumentable for the audit tasks and for measuring storage/compute cost of checkpoints on the student's workflow.

2. **Crab: A Semantics-Aware Checkpoint/Restore Runtime for Agent Sandboxes** — Tianyuan Wu, Chaokun Chang, Lunxi Cao, Wei Gao, Wei Wang (2026) arXiv preprint arXiv:2604.28138 [cs.OS] (submitted 30 Apr 2026; 15 pages, 21 figures)
   https://arxiv.org/abs/2604.28138
   family: checkpoint
   Crab addresses checkpoint/restore for autonomous agents running in sandboxes, identifying a semantic gap: agent frameworks cannot see OS-level effects and the OS has no turn-level context. It is a host-side runtime that uses eBPF inspection to classify the OS effects of each agent turn and decide whether (and what) to checkpoint, built on CRIU/OpenZFS/runc. On shell (Terminal-Bench) and code-repair (SWE-bench) workloads it reaches 100% recovery correctness versus 8% for chat-only state, cuts checkpoint traffic by up to 87%, and keeps overhead within 1.9% of fault-free execution.
   relevance: Provides the clearest empirical evidence for the storage-vs-fidelity trade-off inside the checkpoint family: chat-only snapshots (AutoGen/LangGraph-style thread state) recover correctly only 6-13% of the time on Terminal-Bench and 9% on SWE-bench, chat+filesystem gets 28-42% / 100%, and full FS+process state gets 100%. This maps directly onto the execution-reconstruction audit task ('what must a checkpoint contain to faithfully rebuild step k?') and gives a template for a 'record fidelity' metric. It reports latency and traffic reduction but not absolute checkpoint sizes, so storage numbers must come from elsewhere (e.g. DeltaBox).

3. **DeltaBox: Scaling Stateful AI Agents with Millisecond-Level Sandbox Checkpoint/Rollback** — Yunpeng Dong, Jingkai He, Shiqi Liu, Yuze Hou, Dong Du, Zhonghu Xu, Si Yu, Baochuan Yang, Yubin Xia, Haibo Chen (2026) arXiv preprint arXiv:2605.22781 [cs.OS, cs.AI] (v1 21 May 2026, v2 8 Jun 2026)
   https://arxiv.org/abs/2605.22781
   family: checkpoint
   DeltaBox observes that successive checkpoints of an AI agent's sandbox are highly similar, so it checkpoints changes rather than duplicating full state. It introduces DeltaFS (delta-based filesystem snapshots) and DeltaCR (delta-based process-state checkpoint/restore), keeping filesystem and memory state consistently paired. On SWE-bench trajectories and RL/tree-search (MCTS) workloads it achieves roughly 10-14 ms checkpoints and 2-5 ms rollbacks, about 480x faster restore than E2B's incremental snapshots, reducing state-management overhead from 23-48% to 1-2%.
   relevance: Supplies the cost side of the checkpoint family for the storage and compute axes: delta encoding makes per-step OS-level snapshots cheap enough that forking a sandbox for counterfactual exploration is practical (the OS-level analogue of cheaply forking a log). It contains no auditing, logging or forensic evaluation, so it should be cited for cost/feasibility only, and its delta representation raises a point for the paper: reconstructing state at step k from deltas requires replaying a chain, which blurs the checkpoint/log boundary.

4. **ACRFence: Preventing Semantic Rollback Attacks in Agent Checkpoint-Restore** — Yusheng Zheng, Yiwei Yang, Wei Zhang, Andi Quinn (2026) arXiv preprint arXiv:2603.20625 [cs.CR] (submitted 21 Mar 2026); comments field says 'CoDAIM workshop 2026'
   https://arxiv.org/abs/2603.20625
   family: checkpoint
   The paper shows that checkpoint-restore in LLM agent frameworks breaks the assumption that a retried tool call is identical to the original: after restore, the LLM re-synthesizes subtly different requests, which servers treat as new, causing duplicate payments, reuse of consumed credentials and other irreversible side effects ('semantic rollback attacks'). Two attack classes, Action Replay and Authority Resurrection, are validated in a proof of concept and confirmed as acknowledged by maintainers of 12 frameworks (LangGraph, CrewAI, Google ADK, AutoGen, OpenAI Agents, Claude Code, OpenHands, etc.). ACRFence is a framework-agnostic mitigation that records irreversible tool effects (thread/branch id, tool name, arguments, eBPF-captured environment context) and enforces replay-or-fork semantics on restoration.
   relevance: Directly relevant to the policy-compliance and privacy/security axes: it demonstrates an integrity hazard unique to checkpoint-restore that a log-primary architecture replaying cached tool outputs avoids by construction. Its fix - an append-only effect log layered onto checkpoints with replay (return recorded response) or fork (block and require approval) - is itself a checkpoint+log hybrid, which supports the paper's argument that pure checkpoint designs are insufficient for auditable, policy-compliant agents. The catalogue of 12 frameworks is also useful for the survey portion.

5. **Git Context Controller: Manage the Context of LLM-based Agents like Git** — Junde Wu, Minhao Hu, Jiayuan Zhu, Jiazhen Pan, Yuyuan Liu, Min Xu, Yueming Jin (2025 (v1 30 Jul 2025; v2 1 Mar 2026; v3 24 Jul 2026)) arXiv preprint arXiv:2508.00031 [cs.SE]
   https://arxiv.org/abs/2508.00031 | code: https://github.com/ImprintLab/git-context-controller
   family: checkpoint
   GCC treats an agent's context/memory like a version-control repository, exposing COMMIT, BRANCH, MERGE and CONTEXT operations so the agent can checkpoint progress, explore alternatives on branches, and retrieve prior context in a structured way. The framework is evaluated on SWE-Bench Verified, where the authors report over 80% success, ahead of 26 existing systems, and over 13% relative improvement against baseline approaches.
   relevance: An example of checkpoint-as-version-control: commits give coarse execution reconstruction and branches give cheap counterfactual exploration, but the committed content is agent-authored summaries/intent notes rather than verifiable records of what actually happened, so it trades evidence integrity for low storage and easy branching. Useful to contrast with provenance overlays that capture ground-truth tool effects; no audit tasks (localization, evidence tracing, compliance) are evaluated.

6. **ChronoMem: Version Control and Semantic Rollback for Large Language Model Agent Memory** — Yongye Su, Wujiang Xu, Chaoji Zuo, Elisa Bertino (2026) arXiv preprint arXiv:2607.27773 [cs.CL] (v1 30 Jul 2026, v2 5 Aug 2026)
   https://arxiv.org/abs/2607.27773
   family: checkpoint
   ChronoMem is a semantic version-control layer for LLM agent memory, integrated into Google's Agent Development Kit, that commits a whole-memory snapshot at every memory write, keeps structured version histories, and resolves natural-language undo requests to concrete historical versions via hybrid lexical/semantic retrieval, rank fusion and reranking. It introduces a post-exposure evaluation protocol (agent first sees the full interaction history, then is rolled back and must answer/summarize as if later updates never happened) on LoCoMo and MemoryAgentBench with rollback tasks. ChronoMem substantially outperforms prompt-only and retrieval-only baselines on rollback-consistent QA and history summarization.
   relevance: The post-exposure protocol is a ready-made operationalization of the counterfactual-analysis audit task ('behave as if step k onward had not happened'), applied to a snapshot-per-write architecture. It also illustrates that checkpoint granularity (one full-memory snapshot per write) drives storage cost, though the paper only states qualitatively that its log+snapshot design 'trades storage for fast restoration' and gives no quantitative overhead - so the storage claim in the term paper should be argued, not cited from here. Note the architecture is itself a log+snapshot hybrid.

7. **FALAT: Tracing Failures in LLM Agent Trajectories via Dependency-Guided Search** — Md Nakhla Rafi, Md Ahasanuzzaman, Dong Jae Kim, Zhijie Wang, Tse-Hsun Chen (2026) arXiv preprint (cs.AI), submitted 30 May 2026; no conference venue listed
   https://arxiv.org/abs/2606.00765
   family: provenance-overlay
   FALAT frames failure attribution in multi-agent LLM trajectories as a dependency-guided search problem. It builds a three-level hierarchical trajectory representation plus an external task prior, assigns typed transition labels (follow_up, redundancy, no_influence, error_shift, correction, dead_end) to prune candidates, then searches and verifies whether correcting a candidate step would recover the expected outcome, followed by an adversarial local re-search that classifies steps as Root_Cause, Propagation, Symptom or Contributing. On Who&When it reports 46.0% step-level accuracy on algorithm-generated and 29.1% on hand-crafted trajectories (GPT-5.4-Mini, DeepSeek V3.2, MiniMax 2.5 as base models).
   relevance: FALAT is a clean example of the post-hoc provenance-overlay pattern: it reconstructs typed dependencies from a flat log and uses them to separate error-introducing from error-propagating steps, which is exactly the failure-localization audit task. Its step-level Who&When numbers (46.0% / 29.1%) and its explicit counterfactual-sufficiency check give the term paper a concrete reference point and a warning that overlay reconstruction from a flat log is itself an LLM inference with limited accuracy, so the overlay's storage savings come at a compute and reliability cost.

8. **EDGE: Error Dependency Graph-Guided Multi-Error Attribution in Multi-Agent LLM Systems** — Jun Hou, Priya Pitre, Yi Fang, Xuan Wang (2026) EMNLP 2026 (per arXiv comments field and the GitHub README); arXiv:2609.01360, submitted 1 Sep 2026
   https://arxiv.org/abs/2609.01360 | code: https://github.com/JuneHou/EDGE
   family: provenance-overlay
   EDGE argues that agent failures usually contain several related errors, and that existing attribution methods find a single responsible agent/step but do not model dependencies between errors. It builds an error dependency graph in three stages: an observational graph via Suppes-style temporal-priority and probability-raising screening over co-occurring error categories across traces, a sparse causal-candidate DAG via CAPRI-style AIC pruning, and a validated graph obtained by counterfactual rollout (LLM repair of the source error with tool outputs held fixed, then two judges checking whether downstream errors persist). The validated graph guides a two-stage LLM-as-judge detector, improving multi-error attribution on TRAIL and MAST across several models.
   relevance: EDGE is the one verified paper that couples the failure-localization and counterfactual-analysis audit tasks, using controlled counterfactual rollout to validate dependency edges. An important nuance for the term paper: its graph is a corpus-level graph over error categories learned across many traces, not a per-execution provenance graph, so it should be cited as a population-level overlay that guides per-trace detection rather than as a per-run provenance record. It also illustrates the compute cost of counterfactual validation (repair plus rollout plus double judging per edge).

9. **Adaptive Influence Graphs for Failure Attribution in Multi-Agent Systems** — Yarden Bakish, Amir Dudai, Roy Ganz, Oren Nuriel, Elad Ben Avraham, Mor Shpigel Nacson, Ron Litman (Tel Aviv University and AWS Agentic AI) (2026) arXiv preprint (cs.AI), submitted 25 Aug 2026; no conference venue listed
   https://arxiv.org/abs/2608.24361
   family: provenance-overlay
   The paper introduces Adaptive Influence Graphs (AIGs), a two-stage agentic framework: a Builder transforms a failed trace into a structured graph, choosing node boundaries and influence structure adaptively per trace with a critic-refiner loop, and a Reader agent navigates the graph selectively, verifying edge claims against the original logs and tracing backward through inheritance links to the critical error. Richer trace representations consistently improve attribution across models, and AIGs set a new state of the art on Who&When (55.20% step accuracy on the algorithm-generated partition vs. prior 51.60%; 29.31% on hand-crafted, with Opus-5 as the primary model; 54.76% GPT-5.6-sol, 53.97% Sonnet-4, 53.17% DeepSeek-V3.2).
   relevance: AIG is the most direct prior evidence for the term paper's core hypothesis that a provenance overlay beats a raw log for failure localization: its headline claim is that attribution depends on how the trace is represented and explored, not only on the diagnosing model. It is therefore both a baseline the term paper must position against and a source of the Who&When numbers for calibration. Note that the Reader verifies edges against the original log, which means the overlay is used alongside the log rather than replacing it, a point that bears on the storage trade-off.

10. **AgentTether: Graph-Guided Diagnosis and Runtime Intervention for Reliable LLM Agent Operation** — Chenyu Zhao, Shenglin Zhang, Wenwei Gu, Yongqian Sun, Dan Pei, Chetan Bansal, Saravan Rajmohan, Minghua Ma (Nankai University, Tsinghua University, Microsoft) (2026) arXiv preprint (cs.SE), submitted 7 Jul 2026; no conference venue listed
   https://arxiv.org/abs/2607.06273 | code: https://anonymous.4open.science/r/AgentTether-9416/
   family: provenance-overlay
   AgentTether is a runtime repair framework for multi-step, stateful tool-use agents that performs post-run diagnosis without modifying the agent or environment. It compresses the raw event stream into Transition Units (observation, belief, action, feedback), links them in a dependency-aware Critical Transition Graph with temporal and information-flow edges, and combines an offline behavioral model with graph-based detection to localize the failure-critical step. The diagnosis is turned into behavioral guidance injected at the next retry, with a Check-Decide-Inject harness guarding against drift; on 261 tau-bench tasks (retail, airline, banking) it repairs 59.04% of initially failed Qwen3.7-max and 65.12% of failed GPT-5.4 banking tasks.
   relevance: AgentTether bridges the overlay family and counterfactual/repair analysis: the Critical Transition Graph is a post-hoc provenance overlay used for failure localization, and the guided re-execution is a practical form of counterfactual analysis (does the run succeed once the diagnosed step is corrected?). Because it works on an unmodified agent and environment, it is a useful data point for the term paper's complexity trade-off, and its tau-bench setting gives a standard tool-use benchmark to contrast with the Who&When-centric failure-attribution papers.

11. **Counterfactual Trace Auditing of LLM Agent Skills** — Xiaolin Zhou, Jinbo Liu, Li Li, Ryan A. Rossi, Xiyang Hu (2026) arXiv preprint (cs.AI), v1 12 May 2026, v2 28 May 2026; GitHub README describes it as an anonymized NeurIPS 2026 submission (not confirmed as accepted)
   https://arxiv.org/abs/2605.11946 | code: https://github.com/WillChow66/CTA
   family: benchmark-or-metric
   The paper proposes Counterfactual Trace Auditing (CTA), a framework for characterizing how a skill changes an agent's behavior by pairing traces with and without the skill, segmenting each into goal-directed phases, aligning the phases, and emitting structured annotations of behavioral effects. Applied to 49 software-engineering tasks with Claude, pass rates barely move (+0.3%) yet 522 behavioral-pattern instances are found, including template copying, excess planning and task recovery that aggregate metrics miss; high-baseline tasks show large skill effects despite saturated pass rates, while mid-range tasks show recoverable gains at higher token cost.
   relevance: CTA shows that the counterfactual-analysis audit task can be operationalized purely post hoc from paired traces, with no fork/replay or checkpoint infrastructure, which makes it a useful contrast to checkpoint-based forking and a cheap template the term paper could adopt for its own counterfactual audit. Its finding that outcome metrics hide most behavioral effects also supports the argument that log-primary auditing needs structure (phase segmentation and alignment) layered on top of raw traces to be useful.

12. **Workflow as Knowledge: Semantic Persistence for LLM-Mediated Workflows** — Emanuele Quinto (UNHCR, Copenhagen), Carlo Andrea Rozzi (CNR Istituto Nanoscienze, Modena), Francesco Zanitti (ZeLe & F ApS, Copenhagen) (2026) arXiv preprint (cs.AI, cs.PL, cs.SE), submitted 9 Jul 2026, 39 pages, 18 figures, CC BY-SA 4.0; no conference venue listed
   https://arxiv.org/abs/2607.08740
   family: checkpoint
   The paper proposes a conceptual, Lisp-inspired model in which LLM-mediated workflows are persisted as knowledge objects rather than only producing outputs and traces: workflow definitions and instances, inference records, context snapshots (the bounded material visible at a decision), approval and panel records, dependency links and derived objects. Its central boundary separates derive (deterministic, testable, replayable computation over workflow state) from infer (LLM judgment under declared context), so that model output is recorded as an inference result and never gains direct authority over workflow transitions. The authors state explicitly that the proposal is conceptual, with implementation and empirical evaluation left for future work.
   relevance: This is the clearest verified example of a hybrid that combines checkpoint-style context snapshots with overlay-style dependency links and log-style inference records, which makes it a good citation when arguing that the three families are complementary rather than mutually exclusive. The derive/infer distinction is also directly relevant to execution reconstruction and policy compliance, since it marks which steps are replayable deterministically and which require the recorded LLM context. Its lack of any evaluation means it can only support the conceptual framing, not any empirical trade-off claim.

14. **GRADE: Graph Representation of LLM Agent Dependency and Execution** — Yue Zhao (2026 (submitted June 22, 2026)) arXiv preprint (cs.LG), 18 pages, 5 figures, 8 tables; no peer-reviewed venue listed
   https://arxiv.org/abs/2606.22741 | code: https://github.com/yzhao062/grade
   family: provenance-overlay
   GRADE models an LLM-agent run as a typed graph with two edge layers: an execution layer giving step ordering, read directly from the trace, and a dependency layer capturing what each step relied on, which traces do not record and which is reconstructed with each edge graded as observed, declared, or inferred. Across six corpora spanning tool use (tau-bench, tau2-bench), coding (SWE-agent, SWE-Gym, OpenHands) and web tasks (AgentRewardBench), the dependency layer predicts failure where run size does not, the execution layer localizes where a run fails, and the representation transfers across domains. The paper also explains why standard GNNs struggle on these graphs and offers a feature-based alternative.
   relevance: GRADE is the canonical post-hoc provenance overlay: it is built after the run from existing (log-primary) traces, so it directly represents the 'log first, reconstruct later' end of the design space and its observed/declared/inferred edge grades give a ready-made vocabulary for how much of the dependency structure a log-primary architecture can recover. Its explicit admission that ground-truth reliance labels do not exist at scale is the measurement gap a controlled workflow with inline capture (e.g., Flowcept or VeriGraph) can fill by comparing inferred edges to observed ones. Its failure-prediction and step-level fault-localization experiments map onto the failure-localization audit task.

16. **LEDGER: Claim-to-Evidence Trace Graphs for Auditing LLM Agents** — Daehong Kim (Carnegie Mellon University), Haichao Miao (Lawrence Livermore National Laboratory), Shusen Liu (Lawrence Livermore National Laboratory) (2026 (submitted August 19, 2026)) arXiv preprint (cs.HC, cs.AI); no venue listed
   https://arxiv.org/abs/2608.18398
   family: provenance-overlay
   LEDGER (Layered Evidence and Decision Graphs for Execution Review) is a tracing and review system that builds layered trace graphs over observed agent sessions. It preserves raw Trace Records, groups them into Evidence Nodes and Workflow Nodes (context, plan, inspect, execute, validate, claim), treats artifacts as evidence anchors, and adds typed semantic edges (frames, uses, produces, informs, checked_by, supports) linking claims to the actions, artifacts and checks that support them. 17. **VeriGraph: Towards Verifiable Data-Analytic Agents** — Jiajie Jin, Zhao Yang, Wenle Liao, Yuyang Hu, Guanting Dong, Xiaoxi Li, Yutao Zhu, Zhicheng Dou (2026 (submitted June 15, 2026)) arXiv preprint (cs.CL, cs.AI), 10 pages; no venue listed
   https://arxiv.org/abs/2606.16603 | code: https://github.com/ignorejjj/VeriGraph
   family: provenance-overlay
   VeriGraph addresses the lack of verifiability in data-analytic LLM agents whose reasoning is recorded only as linear text trajectories. The agent instead constructs an explicit heterogeneous evidence DAG during execution, using computational, grounding and derivational expansion primitives to link raw data, interpreter variables, computed results and natural-language claims; graph construction is trained with policy optimization balancing answer correctness, computational integrity and derivational coherence.    relevance: VeriGraph is the fully-instrumented inline overlay in which the agent itself emits the provenance graph as it runs, so evidence tracing reduces to graph reachability from sources to terminal claims with no post-hoc inference; it therefore serves as the upper-bound baseline for the evidence-tracing task and as the sharpest contrast to GRADE-style reconstruction. Its published metric (claim-level Grounding Rate) and public code/model give the term paper a reusable measurement and a runnable system, while its dependence on a specially trained 8B policy illustrates the compute and generality costs of pushing provenance capture into the agent rather than into logs or checkpoints.

18. **Reasoning Provenance for Autonomous AI Agents: Structured Behavioral Analytics Beyond State Checkpoints and Execution Traces** — Neelmani Vispute, Aditya Kadam (Oracle Cloud Infrastructure) (2026 (v1 March 23, 2026; v2 April 10, 2026)) arXiv preprint (cs.AI, cs.DC, cs.SE), 10 pages, 2 tables, 1 figure; explicitly labeled preprint, no venue
   https://arxiv.org/abs/2603.21692
   family: cross-cutting

19. **Causal Agent Replay: Counterfactual Attribution for LLM-Agent Failures** — Jaineet Shah (2026) arXiv preprint (arXiv:2606.08275, cs.LG), v1 submitted 6 June 2026; no conference venue stated
   https://arxiv.org/abs/2606.08275 | code: https://github.com/jaineet17/causal-agent-replay
   family: cross-cutting
   Argues that identifying which step caused an LLM-agent failure requires causal intervention rather than observability or LLM-judge attribution (the latter reaching only ~14% accuracy on the Who&When benchmark). CAR models an agent run as a structural causal model, applies do-interventions (resample, force, replace tool result, edit context) to a step, and re-executes the trajectory forward under the same stochastic policy to measure the shift in outcome distribution. It contributes an intervention algebra, a contrastive estimator with a point-of-commitment rule, and a budget-bounded Monte-Carlo Shapley estimator with confidence intervals; validation is on synthetic SCMs with planted ground truth (pivotal-step and two-step-interaction cases), not on real agent benchmarks.
   relevance: Gives the term paper a formal definition of the counterfactual-analysis audit task (do-intervention plus forward re-execution) and explicitly adopts the record-replay debugger discipline ('record every nondeterministic input so that deterministic glue can be re-executed'), which is exactly what a log-primary substrate provides. It therefore serves as the method layer whose feasibility and cost (number of re-executions, Shapley budget) can be compared across log-primary, checkpoint, and provenance-overlay designs. Caveat for the paper: CAR's own validation is synthetic, so any claim about its accuracy on real traces should be hedged.
